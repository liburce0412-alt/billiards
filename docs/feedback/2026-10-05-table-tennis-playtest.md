## 用户确认的近期迭代方式

在可玩性尚未成熟的阶段，优先改进球感、操作、动作与视觉表现，完成最小必要的构建和明显故障检查后，
沿用已有部署授权直接上线，由用户真实试打、试玩，再根据反馈继续迭代。
不默认展开大批自动回归、性能采样、多设备或联机矩阵验证；只有具体改动或已知问题确实需要时才做有针对性的检查。
不要把更多测试数量当作可玩性提升，也不要在基本手感尚未成立时反复消耗时间证明现有实现。
这是一项迭代流程约定，本条记录本身不表示上述问题已修复或已有新版本发布。

## 追加反馈：局内可见性、动态视野与共用前端

用户补充强调：局内可见性一定要高；球员移动时视野可以随之移动，并有自然的镜头晃动感；
优先真实的 3D 运动体验。结合连续上下文，本条按当前乒乓球模式记录，台球作为可复用的体验与平台参考。
本版反馈范围暂收在当前清单。下一轮已加入用户认可的 Caesar v2.1.2 设计语言与补充体验建议：
[共用前端、液态玻璃及实施顺序](../design/2026-10-05-caesar-glass-frontend-plan.md)。
此要求优先于旧的“纸白 SPECTRA”描述，球感、握拍、真实 3D 与局内可见性仍优先。

### 本版体验方向

- 以球、拍、对手和球台的清晰可读为首要目标。场馆灯光和 UI 应服务于判断球路，
  近侧手臂、球拍、比分和提示的摆放须留出观察落点与接球的空间。
- 相机随球员的横向站位平滑移动，保持能看到来球、球网和对侧球台的击球视角。
  走位可加入轻微重心起伏，接触附近收敛到稳定视线；不是将头部骨骼的全部晃动原样传给镜头。
  保留减少动态效果的偏好，让真实感与清楚判断球路同时成立。
- 玻璃 HUD 以用户认可的 Caesar 实际通透效果为基准，与台球共同整理：薄底色、折射/色散、细边缘和局部跟手追光，透出真实场馆。
  保证亮场馆和暗场馆里比分、当前操作都清楚；避免此前整块泛白或整屏压暗的观感。
  次要信息合并进紧凑顶部/菜单，主要操作放在顺手且不挡球的位置。
- 和已记录的托球/抛球/触球物理、握拍与正反手、轻重击与旋转一起构成本版可玩性改进范围。

## 用户反馈原意

1. 页面过于简单；首页两个场馆选择看起来都太暗，像被遮住。
2. 鼠标操作缺少清楚的技术表达：怎样扣杀、发力、轻打、加旋，不能一直只有同一种回球。
3. 球在球拍上看起来像平面圆片，缺少球体感觉。
4. 机器人握拍和正反手姿势怪异，需要参照真人。
5. 球不能贴在拍上；动作、接触、离拍和飞行应符合物理规律。

## 初步原因和改进要求

### 1. 首页、场馆展示与亮度

代码确认：`src/app/table-tennis-route.tsx:272` 的场馆卡片只有文字；
`dist/css/table-tennis-host.css:39`、`:43` 都是深色 CSS 渐变，没有真实场馆预览。
因此这两个选择卡片的暗色有直接实现原因，不能称为高质量场馆展示。
另外 `dist/css/react-app.css:1242` 附近更高权重的通用按钮与 strong 样式使用 `color: inherit`，
会覆盖场馆卡片自身的白字规则，继承主站暗色文字；深色背景再叠暗字会进一步损害可读性。
后续应修正这项样式优先级，而非给用户要求调高显示器亮度。

游戏内另外使用曝光 0.88、环境光和有色雾（`src/browser/scene.ts:88` 附近）。
仅凭静态代码不能断定游戏内发暗一定来自遮罩或曝光；暂停菜单确有暗色模糊遮罩，
正常游戏是否误留遮罩需要以后实际观察，本轮不做复测。

后续要求：用最终游戏内实景制作场馆预览，让赛博馆的灯光层次与体育馆的明亮空间一眼可分；
文字只局部加底衬，不压暗整张图。页面增加有用的操作入口与技术说明，保持主次明确。

### 2. 控制方式与不同击球技术

代码确认：`src/browser/input.ts:11` 的鼠标拖动以平均移动速度映射力度，横向位移映射目标方向，
竖向位移映射一个有正负的旋转参数。松开鼠标提交动作；很短的拖动被忽略。
空格使用固定力度 0.5、固定旋转 0.15，界面发球按钮使用力度 0.46、旋转 0.1。
这些映射没有形成清楚、可独立控制的扣杀、轻挡、搓球、拉球和侧旋操作。

当前回球还会把横向瞄准量写入侧旋，想打斜线和想加侧旋被耦合。
发球水平速度只在 3.8–4.4 m/s 之间变化；接球力度主要改变预设落点的到达时间。
因此“界面有 power/spin 参数”不能当作不同技术已经实现。

后续交互方向（草案，尚未实施）：将落点、拍面角度、挥拍速度和刷球方向分开表达；
慢而短的动作可以轻挡/短球，快速向前是强攻，向上/下的切向动作控制上旋/下旋，侧向刷动控制侧旋。
扣杀还要满足来球高度、触球时机和拍面条件，不应只把“高力度”统一换成扣杀动画。
加入简短的鼠标示范、当前球技/旋转/力度反馈，避免靠说明文字猜操作。

### 3. “平面圆球”和贴拍

代码确认：模型源 `art/build-equipment-and-arenas.py:257` 制作的是半径 0.02 m 的 UV 球体，
并非圆形贴图。但 `src/core/match.ts:106` 的 `resetBallForServe()` 把球心直接复制到球拍位置，
`src/browser/scene.ts` 又把实际球拍击球面中心对齐这个位置，因此准备发球时存在球与拍面的重叠。
这一摆放错误可解释“贴拍、像一片圆”的一部分观感，不能只通过提高模型面数或亮度掩盖。
是否还有法线、投影、光照或材质问题，留待以后实际近景检查。
实际导出 GLB 的只读几何信息也显示 Ball 三轴边界均为 ±0.02 m，1023 个顶点并带法线，
进一步排除了“实际只用了平面精灵”的猜测；这不等于画面观感已经合格。
另外存在待复查路径：触拍被判违规后，判分状态可能将仍显示的球冻结在接触处约 1.1 秒；
这可能造成回合中的短暂贴拍观感，尚未复现，不能称为正常来回球持续吸附的已确认原因。

后续要求：准备发球时球在非持拍手上；抛起后是独立运动物体，击中后立刻离拍。
球体轮廓、受光渐变和接触关系应在近景与运动中都可读；不得固定到球拍节点或长期锁在碰撞面。

### 4. 握拍、正反手与全身动作

横拍/直拍是握法，正手/反手是击球方式。后续先以标准横拍为完整基线，
分别做好正手与反手，而不是把两者做成两种随意握法。

代码确认：当前四根手指使用相同弯曲规则，拇指没有配套的持拍动作；
`scene.ts` 还按 `aimX < -0.15` 选择反手动画，而非来球相对身体的位置、惯用手及击球动作。
运行时为追到碰撞触点会重设拍面朝向及手臂骨架，低球尤其容易显得不自然。
已有 192 姿态检查只证明拍面中心与数学触点接近，不证明正确握拍、关节自然或全身发力合理。

后续要求：把球拍放入 Blender 手掌中精修虎口、拇指、食指及其余三指，校准手柄与前臂关系；
以真人准备、引拍、蹬地/转体、迎球、触球、随挥、回位为参考制作连续动作。
拍面角度应由实际球技与接触条件决定，骨架修正受肩肘腕活动范围约束，不能只让手追一个点。
保留机械人外形，但运动关系采用合理的人体参考。

### 5. 接触物理与发球过程

代码确认：`src/core/match.ts:228` 的发球直接设置球速度，并把挥拍与接触标成同一个 tick，
没有非持拍手托球、抛球、下降及实际拍球接触阶段。
`hitPaddle()`（约 289 行）按目标落点和预设时间反算出球速度；
`physics.ts:70` 附近碰撞使用固定朝向的有限拍面，而非随动画转动的实际拍面法向。
有扫掠碰撞、重力、阻力和受限旋转，但它们不能弥补触球时直接覆盖速度的简化。

后续要求：共享同一份球拍位置、朝向、线速度和角速度供物理与动画使用；
根据相对速度、拍面法向、恢复系数及受限摩擦冲量产生离拍速度和旋转。
辅助站位和瞄准可以保留，但不能在接触后把任意失误强制改写成落在对面台内的轨迹。
高速接触仍需要连续碰撞；离拍后的球要自由飞行，不能吸附、瞬移或为了配合动作延迟弹出。

完整发球应为托球 → 近竖直抛起 → 下降时击球 → 本方台面 → 对方台面。
国际乒联 2026 规则 2.6.1–2.6.3 要求从张开的非持拍手掌起球、无旋抛起至少 16 cm，下降时击打。
参考：[ITTF 2026 规则，第 41 页](https://documents.ittf.sport/sites/default/files/public/2026-02/2026_Statutes_v1_consolidated_clean.pdf#page=41)。
