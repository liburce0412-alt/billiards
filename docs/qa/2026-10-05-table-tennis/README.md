## 三档延迟与桌面参考

`online-latency-test.mjs` 使用 Playwright `routeWebSocket().connectToServer()`，双真实账号连接同一个本地权威 Worker，在客户端上、下行消息各注入 RTT / 2 的交付延迟，未替换协议、快照或游戏状态。`online-latency-report.json` 记录 `2026-10-05T10:02:12.208Z` 至 `10:02:37.123Z` 的最终通过运行：

| 注入 RTT | 真实回合             | 双方同 tick 状态 SHA256 一致 | 结果                     |
| -------- | -------------------- | ---------------------------- | ------------------------ |
| 50 ms    | 发球并成功回击，2 拍 | 66 个快照                    | 两输入 ACK、双方比分一致 |
| 100 ms   | 发球并成功回击，2 拍 | 68 个快照                    | 两输入 ACK、双方比分一致 |
| 150 ms   | 发球并成功回击，2 拍 | 69 个快照                    | 两输入 ACK、双方比分一致 |

三个场景均无页面错误，房间阶段只有等待与进行中，没有再次暂停。截图为 `online-latency-{50,100,150}.png`。这些是对真实客户端和权威服务链路的人工延迟测试，范围是一段发球、回击与得分，不宣称每档都完整打完三局或属于跨网络真机。

前两版测试错误地假定甲一定首先发球，并在准备状态延迟返回时重复点击同一个按钮；按钮随后变成发球，导致意外先发一分。脚本现按照服务器的发球方操作，每个席位只点一次准备。早期报告以 `online-latency-report-<时间戳>.json` 保留。

报告另记录桌面 1280×720、双球场打开时 10 秒 `requestAnimationFrame` 参考：2400 次采样，中位 4.2 ms、P95 4.3 ms。这反映桌面浏览器约 240 Hz 的回调调度；游戏自身限制 60 FPS，**该值不是实际 GPU 帧耗时，更不是移动设备性能验收**。
